Python & Telecommunications Know-How

A practical reference for network programming in Python, written around the TCP/UDP exam tasks (struct-based clients, select servers, UDP servers, proxies). Every code block is runnable Python 3.

1. Python core basics

Python is dynamically typed, indentation defines blocks, and everything is an object. The pieces you need constantly in network code: 

x = 5; name = "alma"            # no declarations
items = [1, 2, 3]               # list (mutable)
pair  = ("almafa", 4)           # tuple (immutable) - struct.unpack returns tuples!
d     = {"1": ["almafa", 4]}    # dict
text, num = d["1"]              # unpacking
for i, v in enumerate(items, start=1): print(i, v)
squares = [n*n for n in items if n > 1]     # comprehension
def f(a, b=2, *args, **kw): return a + b      # defaults, varargs
if __name__ == "__main__":      # run only when executed directly
    main()

Context managers

with guarantees cleanup (closing a socket or file) even on exceptions. Sockets and files both support it. 

with socket.socket() as s:     # s.close() is called automatically
    ...

Slicing

"almafa"[:4]    # 'alma'   first 4 characters
"alma"[::-1]    # 'amla'   reversed
"almafa"[4:]    # 'fa'     drop the first 4
Watch out: the first exam task says "cut X characters from the start" but the examples (almafa,4 → amla) keep the first X characters and reverse them: text[:X][::-1]. When spec text and examples disagree, trust the examples and test against the given server.

2. Strings vs. bytes

Python 3 strictly separates str (Unicode text) from bytes (raw octets). Sockets only transmit bytes.

Operation Code Note
str → bytes "alma".encode("utf-8") Non-ASCII chars (á, ő) take 2+ bytes, so len(text) != len(text.encode())
bytes → str b"alma".decode("utf-8") Raises UnicodeDecodeError on invalid data
Remove padding data.rstrip(b"\0") struct pads 20s with NUL bytes
Number as bytes str(19).encode() → b"19" "Return the value as a byte string" in task 2
Bytes to number int(b"19") int() accepts bytes holding digits

Byte literals: b'INCR'. Indexing bytes gives ints (b'A'[0] == 65), slicing gives bytes.

4. The struct module

Converts between Python values and packed C-style binary records. This is the "wire format" of your protocol.

Code C type Python Size
i / I int / unsigned int 4
h / H short int 2
q long long int 8
f / d float / double float 4 / 8
Ns char[N] bytes N
? bool bool 1

Pack / unpack

import struct
packed = struct.pack("20s i", "almafa".encode(), 4)   # 24 bytes
text, num = struct.unpack("20s i", packed)            # (b'almafa\0\0...', 4)
text = text.rstrip(b"\0").decode()
struct.calcsize("20s i")   # 24
struct.calcsize("4s i")    # 8
struct.calcsize("5s i")    # 12   <- 3 padding bytes after 5s!

Alignment and byte order

With no prefix, struct uses native byte order and native alignment: an i must start at a multiple of 4, so 5s i becomes 5 + 3 pad + 4 = 12 bytes. Prefixes change this:

Prefix Byte order Alignment
(none) / @ native native (padding)
= native none
< little-endian none
> / ! big-endian (network order) none
The exam gives formats like 20s i and 5s i without prefix, so use exactly those strings; changing them changes message sizes and breaks the given server/test environment. In new protocols you design yourself, prefer ! (network byte order).

Dynamic formats

fmt = f"{num}s"                       # e.g. "4s"
data = recv_all(sock, struct.calcsize(fmt))
reply = struct.unpack(fmt, data)[0]   # tuple of one element

If a string is longer than the field, struct.pack silently truncates; shorter is NUL-padded. A value of the wrong type raises struct.error.

5. The socket module

TCP client

import socket
with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as s:
    s.connect(("localhost", 10000))
    s.sendall(payload)            # sendall loops until everything is sent
    data = s.recv(1024)           # up to 1024 bytes, may return fewer!

TCP server

srv = socket.socket()
srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)  # avoid "Address already in use"
srv.bind(("0.0.0.0", 10000))   # 0.0.0.0 = all interfaces, "localhost" = loopback only
srv.listen()
conn, addr = srv.accept()      # blocks; conn is a NEW socket per client
data = conn.recv(1024)         # b"" means the peer closed the connection

UDP

u = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
u.settimeout(3)                         # otherwise recvfrom may block forever
u.sendto(payload, ("localhost", 10001)) # no connect needed
data, addr = u.recvfrom(1024)           # one call = ONE datagram, with sender address
# server side: u.bind((host, port)) then loop recvfrom/sendto(addr)

Reading exactly N bytes (TCP)

TCP is a byte stream: one send of 24 bytes may arrive as 10 + 14 bytes. Always loop: 

def recv_all(sock, n):
    buf = b""
    while len(buf) < n:
        part = sock.recv(n - len(buf))
        if not part: raise ConnectionError("closed")
        buf += part
    return buf

On localhost small messages nearly always arrive whole, which hides this bug until it fails on a real network.

6. I/O multiplexing with select

select.select(rlist, wlist, xlist, timeout) blocks until at least one socket in rlist is readable and returns the ready ones. A listening socket is "readable" when a connection waits in accept(); a client socket is readable when data (or EOF) is available. This allows one thread to serve many clients. 

inputs = [srv]; buffers = {}
while True:
    readable, _, _ = select.select(inputs, [], [])
    for s in readable:
        if s is srv:                       # new connection
            c, _ = srv.accept(); inputs.append(c); buffers[c] = b""
        else:
            data = s.recv(1024)
            if not data:                   # client disconnected
                inputs.remove(s); del buffers[s]; s.close()
            else:
                buffers[s] += data
                while len(buffers[s]) >= SIZE:        # complete message(s)?
                    msg, buffers[s] = buffers[s][:SIZE], buffers[s][SIZE:]
                    handle(s, msg)

Per-client buffers handle partial and coalesced messages, the same stream issue as above. Never call a blocking recv_all inside the loop: one slow client would freeze all others. To combine TCP and UDP in one loop just add the UDP socket to inputs and use recvfrom for it.

Alternatives: selectors (higher-level, uses epoll/kqueue), threading (thread per client), asyncio (coroutines). Shared mutable state in threaded servers needs a Lock; in a select loop it does not, because everything runs in one thread.

7. Errors & debugging

Symptom Likely cause
ConnectionRefusedError Server not running / wrong port or host
OSError: Address already in use Old process or TIME_WAIT: set SO_REUSEADDR, kill old process
struct.error: unpack requires a buffer of N bytes Got fewer/more bytes than calcsize: partial read, wrong format string, or padding
TypeError: a bytes-like object is required Sent a str: call .encode()
socket.timeout UDP datagram lost, server down or wrong address
Hangs forever Both sides in recv (deadlock), or UDP without timeout
Garbage text with \x00 Forgot rstrip(b"\0") 
try:
    data = s.recv(1024)
except (ConnectionResetError, socket.timeout) as e:
    print("network problem:", e)
finally:
    s.close()
print(repr(data), len(data))   # repr shows hidden bytes - the best debugging aid

8. Layered models

OSI layer TCP/IP layer Examples Unit
7 Application, 6 Presentation, 5 Session Application HTTP, DNS, SMTP, your own struct protocol message
4 Transport Transport TCP, UDP segment / datagram
3 Network Internet IP, ICMP packet
2 Data link, 1 Physical Link Ethernet, Wi-Fi, fibre frame / bit

Encapsulation: your 24-byte struct becomes TCP payload; TCP adds a header (ports, sequence numbers), IP adds addresses, Ethernet adds MAC addresses and a CRC. Each layer only talks to the same layer on the peer. A Python socket program lives at the application layer and uses the transport layer through the socket API.

9. IP addressing and ports

  • IPv4: 32 bit (192.168.1.10); IPv6: 128 bit. 127.0.0.1/localhost is loopback: traffic never leaves the machine. 0.0.0.0 as bind address = every interface.
  • Private ranges: 10/8, 172.16/12, 192.168/16, reached from outside only via NAT.
  • Port: 16 bit (0–65535) selecting the application on a host. 0–1023 well-known (80 HTTP, 443 HTTPS, 53 DNS, 22 SSH), 1024–49151 registered, above dynamic. Servers bind to a chosen port; clients get an ephemeral port automatically.
  • A connection is identified by the 5-tuple (protocol, src IP, src port, dst IP, dst port). A TCP port 10000 and a UDP port 10000 are different endpoints, so the exam servers can both use 10000.
  • DNS maps names to IPs (socket.gethostbyname("example.com")).

10. TCP (Transmission Control Protocol)

Connection-oriented, reliable, ordered, byte-stream, flow- and congestion-controlled.

Three-way handshake

Client                    Server
  | ---- SYN (seq=x) ----> |     connect() starts
  | <-- SYN+ACK (y, x+1) - |     server in accept queue after listen()
  | ---- ACK (y+1) ------> |     connect() returns / accept() returns

Teardown uses FIN/ACK in each direction (four-way); close() on one side makes the other side's recv return b"".

Key mechanisms

Mechanism Purpose
Sequence numbers + ACKs Ordering and detecting loss
Retransmission (timeout, fast retransmit) Reliability: lost segments are resent transparently
Sliding window Flow control: receiver advertises free buffer space
Congestion control (slow start, AIMD) Avoid overloading the network
Checksum Detect corrupted segments

No message boundaries: TCP preserves byte order, not the sizes of your send calls (see framing, section 12). The API order is: server socket → bind → listen → accept → recv/send → close; client socket → connect → send/recv → close.

11. UDP (User Datagram Protocol)

Connectionless, unreliable, unordered, message-oriented. The 8-byte header holds source port, destination port, length and checksum. No handshake, no retransmission.

TCP UDP
Connection Yes (handshake) No
Delivery guarantee Yes, in order No: loss, duplication, reordering possible
Boundaries Byte stream One send = one datagram = one recv
Overhead 20+ byte header, state 8 byte header, stateless
Python SOCK_STREAM, connect/accept SOCK_DGRAM, sendto/recvfrom
Typical use Web, email, file transfer DNS, VoIP, video, games, streaming telemetry

Practical consequences: always set a client timeout and decide what to do on loss (retry, report error); the server must remember the client addr from recvfrom to answer; datagrams bigger than the path MTU (~1472 payload bytes on Ethernet) get IP-fragmented, so keep them small.

12. Framing and binary protocols

Since TCP gives a stream, an application protocol must define where a message ends. Common techniques:

Technique Example
Fixed-size records The exam's 4s i (8 bytes) or 20s i (24 bytes): read exactly calcsize bytes
Length prefix 4-byte length, then payload (struct.pack("!I", len(p)) + p)
Delimiter Newline-terminated text (HTTP headers, SMTP, Redis)
Connection close End of data = EOF (HTTP/1.0 bodies)

Designing a message format

  • Text fields: fixed width, NUL-padded (Ns), or length-prefixed.
  • Integers: fixed width and defined byte order (big-endian by convention on networks, "network byte order").
  • Variable-length reply as in task 1: the reply size depends on the request (f"{num}s"), so both sides must derive it identically.
  • Commands as short padded ASCII codes (IN, INCR, DECR), which is why you must strip NULs and compare after decode().

Replies can be a text byte string (b"19", task 2: the client needs to know how to read it, here: one recv and int()) or a packed struct (struct.pack("i", 19), task 3a). Text replies without delimiter are fragile with TCP; in a real protocol add a newline or length prefix.

14. Proxies and multi-actor systems

A proxy is a server towards the client and a client towards the real server. In task 3c the TCP server holds no state: it receives (IN|INCR|DECR, X), translates the command (IN→PUSH, INCR→PLUS, DECR→MINUS), re-encodes it (5s i), sends it by UDP, waits for the i reply, converts it to a byte string and returns it over TCP. 

client --TCP "4s i"--> [proxy] --UDP "5s i"--> [UDP server: stores value]
client <--TCP bytes--- [proxy] <--UDP "i"----- [UDP server]

This is protocol translation plus centralised state: several front-ends can share one authoritative backend. Design points: timeouts towards the backend (UDP can lose packets), error replies to the client, one UDP socket reused for all requests (fine in a single-threaded loop). Other proxy roles: caching, load balancing, TLS termination, firewalling, anonymisation.

Checker / monitor clients

Task 3b compares two systems that should hold the same state. Using a neutral operation (add 0) reads the value without changing it. Because the faulty UDP server adds -1/0/+1 to every command, errors accumulate, so the values diverge once and stay different; a checker detects it only if the servers were in sync before.

15. Reliability, errors and testing

  • Error detection: parity, checksums (IP/TCP/UDP use a 16-bit ones'-complement sum), CRC (Ethernet). Correction: ARQ (retransmit) or FEC (redundant coding).
  • ARQ variants: stop-and-wait, go-back-N, selective repeat. TCP is a sliding-window selective-ack hybrid.
  • Making UDP reliable: sequence numbers + ACK + retry with timeout + duplicate suppression. Beware retrying non-idempotent commands (PLUS 5 executed twice = +10); design idempotent operations (PUSH) or attach request IDs.
  • Latency vs. throughput: RTT is the round-trip time; throughput ≈ window / RTT. Bandwidth-delay product = bandwidth × RTT.
  • Fault injection (as the faulty UDP server) is a standard testing technique: deliberately break a component to verify that monitors detect it.
  • Security: plain TCP/UDP is unencrypted; use TLS (ssl module) in real systems; validate lengths and values of incoming data, never trust the peer.
